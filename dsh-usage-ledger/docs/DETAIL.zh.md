## 会话视图（会话页「用量」标签）

每个会话页新增「用量」标签（`conversation.view` 挂载位），展示该会话自身的用量分解——内容对齐 token-total 的会话视图，但去掉了它的「请求记录」栏（用户明确的设计决定）：

- **六指标卡**：请求（含失败次数与失败率）、Tokens 总量 / 输入 / 输出、缓存命中率（三个 prompt 桶中 cache-read 的占比）、解码速度（附平均首 token 等待）。
- **子会话表**：后代会话行（名称、请求、tokens、缓存命中率、类型）。数据来源是永久 KV 会话索引，SQLite 明细后端降级时同样可用。
- **模型表**：每行请求次数加输入 / 输出 / 缓存读 / 缓存写四个 token 桶与命中率，由对会话及其后代的 SQLite 无上限 `GROUP BY` 聚合（不受明细条数上限截断）。依赖明细后端，降级时为空；工具 chips 同理。
- **实时头部**：2 秒串行轮询（同一时刻至多一个在途请求；标签页恢复可见时立即补一次请求），显示最近一次成功读取的时间戳，并附一个绝不会卡在在途轮询后面的手动刷新按钮。轮询失败时保留最近一次好数据。

## 回填语义（禁用 / 重装 / 升级）

- **延迟的存活会话**：回填扫描到达时仍存活（窗口未关）且尚未记录存活边界的会话会被**延迟**——暂不写入游标，待其关闭后由后续扫描全量回放。状态在 `/status` → `backfill.deferredSessions` 中展示。
- **离线窗口补洞**：插件被禁用、卸载或升级期间持久化的事件，会在下次激活时补回（存活链路首次观测到的位置与会话行 `lastSeq` 高水位对比，差额从日志回放）。事实按幂等 upsert 写入，过时的高水位至多导致重复回放，绝不重复计数。
- **启动期对账 sweep**：主历史扫描结束后，每个游标已标记且当前不存活的会话都会与会话行的 `lastSeq` 高水位对账。完全没有行（旧版零标记 bug 的受害者）→ 从 seq 0 全量回放整条日志；行高水位低于日志最大 seq（插件完全离线期间持续持久化事件、随后关闭的会话）→ 回放高水位之后的开放尾部；否则该会话已记账，仅产生一次只读日志扫描。存活会话与延迟会话一律不碰——它们归存活链路所有。对账结果在 `/status` → `backfill.sweep`（`{checked, replayed}`）中报告；`/usage-ledger/api/reset`（清空 + 全量重扫）仍可作为手动兜底手段。
- **继承前缀回放**：回放无条件跳过宿主报告的 `inheritedEventCount` 切点之前的前缀。宿主保证该切点大于 0 当且仅当会话是 seeded——包括 UI fork 出的、header 里没有 parentSession 的 seeded 子会话；未 seed 会话的切点恒为 0，跳过对它是空操作，其整条日志（完整的正史）天然全量回放。seeded 子会话被跳过的前缀归其父会话自己的回放所有（实测一个 seeded 子会话与父会话日志重叠约 6.3M token），跳过正是为了防止跨会话重复计数。
- **降级（纯 KV）模式限制**：SQLite 明细后端打开失败时，插件降级为纯 KV 运行，delta 基准退回进程内 recent-facts Map（上限 10000、FIFO 淘汰，并随 30 天保留窗口的 prune 语义一同丢弃窗口外事实）。该降级模式下，对保留窗口外旧事实的再次回放仍可能使 KV 计数重复累加——与 0.1.3 已修复的 SQLite 正常模式双计缺陷同类。正常模式下永久 delta 锚（request / tool / turn anchor）不受 prune 影响且覆盖全部重放路径；降级模式建议尽快恢复 SQLite 后端（重挂载 / 重启），并执行一次 `POST /usage-ledger/api/reset` 重建校准。
- **跨 prune 窗口的重放幂等（0.1.3）**：KV rollup 的 upsert delta 基准是 SQLite 中的**永久锚行**（`request_anchor` / `tool_anchor` / `turn_anchor`），而不再是 30 天滚动的明细行。prune 只删明细行，锚跨 prune 存活；只有 `/reset` 会清锚（它同时清空 KV 侧，两者始终配对）。因此对任何已入账事实的再次回放，即使其明细行已被 prune，delta 也严格为 0；turn 标记按 `(session, seq)` 去重。0.1.3 之前 delta 基准是可被 prune 清空的明细行，prune 之后再回放旧事实时 old 为 null、对永久 rollup 盲目累加——发布验收实测 6 天恰好 2×（全部是 30 天截止之前的旧数据，触发路径是重挂载窗口后 sweep 重放了高水位读落后的会话）。现在 sweep 与 prune 的交互在两个方向上都安全：已追平的会话只花一次只读扫描；落后或标记陈旧的会话全量重放也严格幂等。`/status` 以 `anchorRows` 报告锚行数。0.1.5 起，`/reset` 的存活会话边界水位线改在 store 串行队列的 reset job 内、清空前一刻采样——采样与清空之间不再存在可漏记事件的亚秒窗口（此前窗口内被存活链路观测并计入 KV 的事件会被清空，又因 seq ≥ 边界不被重扫回放、也不会被存活链路重新观测，从而永久漏记）。
